# File Tidy

给本地资料库生成**整理方案**：把散落、乱名、无日期的文件理成一个能找得回的结构。

## 何时使用

- 用户说「帮我整理一下这些文件」「太乱了，按年份/项目分一下」「这些名字看不出是什么」。
- 用户抱怨「找不到东西」而索引覆盖正常——问题在结构，不在检索。

不要主动使用。整理是破坏性话题，用户没提就不要碰。

## 铁律（本阶段）

**只能出方案，绝对不能动文件。** 插件当前**没有**执行能力：不移动、不重命名、不删除。

- 不许说「已经整理好」「已重命名」——你只产出了一个 JSON 方案。
- 不许用 bash/python 自己写脚本来移动文件绕过这条限制。
- 用户如果要求「直接执行」，如实回答：执行与撤销是待做的独立步骤，现在只能给方案。

## 流程

1. **确认索引**：`file_recall_index { action: "status" }`。
   - `roots` 为空 → 先问资料在哪个文件夹，`configure` + `build` 之后再继续。
   - `files` 为 0 → 先建库，方案没意义。
2. **生成方案**：`file_recall_tidy { action: "plan" }`。
3. **汇报**（必须按这个结构，不要贴整份 JSON）：
   - 一句话总量：`files` 个文件、`moves` 条移动建议、`renames` 条改名建议。
   - **前 5–10 条样例**，每条写成 `原相对路径 → 建议路径`，并附上 `reason`。
   - 只报告不动的事项：重复文件名（`duplicates`）、文件过多的文件夹（`overloaded`）。
   - 方案文件路径：`planPath`（用户可以直接打开看全部 400 条）。
4. **交付风险，用用户能懂的话说清**（不可省略）：
   - 改名会**断开** Obsidian 双链、其他软件里的引用；纯文件夹没有这个问题。
   - iCloud / OneDrive / Dropbox 里大量改名可能产生冲突副本。
   - macOS 权限（TCC）可能让部分文件在真正执行时失败。
   - 日期前缀来自文件的**修改时间**，可能与内容真实日期不符（例如拷来拷去会改 mtime），所以这是"低置信度"建议，需要用户判断。
5. **等用户决定**。问一句「要我继续做执行能力吗，还是先把方案里的规则调一调」。

## 规则说明（用户问起来时）

- 移动：只把**根目录散落**的文件收进 `整理归档/`，不跨目录搬运、不改层级。
- 改名：**只加前缀**，形如 `2023-05-01_原名.pdf`。原名一个字都不改，所以随时能改回去、也能搜到原来的词。
- 触发改名的两种情况：名字是相机/扫描仪自动生成的（`IMG_2034`、`扫描件 001`、`微信图片…`），或名字与所在目录都**没有任何时间信息**。
- 已经有年份（名字或父目录里）的文件不动。
- 重复文件名、文件夹文件过多：**只报告**，不合并、不删除。

## 空态处理

- `actions` 为空：直接说「结构已经够干净，没找到需要动的地方」，不要硬凑建议。
- `truncated: true`：说明方案超过 400 条上限，只列了前面的；建议先按子目录分批整理。
